锁、死锁与时间戳排序Locks, deadlocks and timestamp ordering

对应 A2 专项：并发竞争与死锁 / Assignment connection →

学习目标与锁的作用Learning objectives and the purpose of locking

来源 / Source: Lecture/Week11-CC.pdf · PDF p. 3-17（原资料留在本地版） · 本地逐页图文 / Local pages

目标是给事务加入合适读写锁，比较四种2PL，画等待图检测死锁，并逐行执行时间戳排序。前置是第10章的冲突、图与恢复性质。锁（lock）是对数据访问权限的协调状态，DBMS锁管理器记录谁持有什么、谁在等待；锁不是把数据复制到另一个表，也不是简单看到冲突就必须终止。

The goal is to add read/write locks, compare four 2 PL variants, detect deadlocks with wait-for graphs and execute timestamp ordering stepwise. Prerequisites are conflicts, graphs and recoverability from Chapter 10. A lock coordinates access permissions; the lock manager records holders and waiters. Locking does not copy data into another table, nor does every conflict require immediate abortion.

共享锁（shared/read lock，S）允许多个事务同时读；排他锁（exclusive/write lock，X）只允许一个事务访问受保护项以修改。S与S兼容，S与X、X与X不兼容。持X通常已足够读，无需再申请S。S升级X时必须等其他读者释放；若两个读者都想升级，可能互等。

A shared/read lock (S) permits concurrent readers. An exclusive/write lock (X) grants one transaction modification access. S is compatible with S, but S/X and X/X are incompatible. An X holder can normally read without requesting S. Upgrading S to X must wait for other readers, and two upgrading readers can wait for one another.

仅在每次读写前加锁、事后随手解锁仍可能不串行化。例如T1读完X就解锁，T2改X，T1之后又获取Y锁继续依赖旧状态，可能形成冲突环。协议的关键是约束加锁与解锁的相对位置，而非只有“存在锁”。

Locking before each operation and casually unlocking afterwards can still produce nonserialisable schedules. If T1 releases X after reading, T2 changes it, and T1 later acquires Y while relying on old state, a conflict cycle can arise. The protocol must constrain relative lock and unlock positions; lock existence alone is insufficient.

两阶段锁：增长、锁点与收缩Two-phase locking: growth, lock point and shrinkage

来源 / Source: Lecture/Week11-CC.pdf · PDF p. 18-24（原资料留在本地版） · 本地逐页图文 / Local pages

两阶段锁（two-phase locking，2PL）把每个事务分成增长期和收缩期：第一次释放锁之前可申请/升级，之后只能释放/降级，不能再申请新锁或升级。锁点（lock point）是获取最后一个锁的时刻。把所有事务按锁点排序，可得到它们冲突等价的串行顺序，因此2PL保证冲突可串行化。

Two-phase locking (2 PL) divides each transaction into growth and shrinkage. Before the first release it can acquire or upgrade locks; afterwards it can only release or downgrade, without new acquisitions or upgrades. The lock point is its final acquisition. Ordering transactions by lock points gives a conflict-equivalent serial order, explaining why 2 PL guarantees conflict serialisability.

锁降级X→S已释放一部分访问权，属于收缩；升级S→X属于增长。若先降级Y再获取X的锁，就违反2PL。可把X锁提前到降级前，或把降级推迟，但必须保留原读写的程序顺序。2PL只限制锁动作，不要求事务一定先把所有数据读完才开始写。

Downgrading X→S releases permission and starts shrinkage; upgrading S→X belongs to growth. Downgrading Y before acquiring X violates 2 PL. Acquire X earlier or postpone the downgrade while preserving the original read/write program order. 2 PL constrains lock actions, not a rule that all reads must precede all writes.

Strict与Rigorous不可混称：Strict允许某些S锁在满足2PL的条件下提前释放，Rigorous把所有锁留到结束。保守2PL消除的是持部分资源再等另一部分造成的环；若实现成逐个尝试并一直持住部分锁，就失去其“全有或全无”的保证。

Strict and Rigorous differ: Strict can release some S locks early while respecting 2 PL, whereas Rigorous retains all locks until termination. Conservative 2 PL removes cycles caused by holding partial resources while waiting for more. An implementation that incrementally acquires and retains partial sets loses its all-or-nothing guarantee.

死锁、饥饿与等待图Deadlock, starvation and wait-for graphs

来源 / Source: Lecture/Week11-CC.pdf · PDF p. 25-39（原资料留在本地版） · 本地逐页图文 / Local pages

死锁（deadlock）是互相等待，等待图（wait-for graph）Ti→Tj表示Ti正在等Tj释放锁；有环即有死锁。它与优先图不同：优先图边表示已经发生的冲突先后，等待图边表示当前阻塞依赖。T1先写X，T2要读X时，优先约束可能是T1→T2，而当前等待边是T2→T1。

A deadlock is circular waiting. In a wait-for graph, Ti→Tj means Ti is waiting for Tj to release a lock; a cycle indicates deadlock. A precedence graph instead describes ordering constraints from operations already performed. If T1 writes X and T2 wants to read it, the precedence constraint can be T1→T2 while the current waiting edge is T2→T1.

完整例子：T1持X(A)，T2持X(B)。T1申请X(B)被阻塞，画T1→T2；T2申请X(A)被阻塞，画T2→T1，形成环。DBMS选择牺牲者回滚，释放它的锁让另一方继续；不能假装被阻塞的写已经执行后再画图。牺牲者选择与重启时机依实现，除非有实际日志，不应断言一定回滚T1。

Worked example: T1 holds X(A), T2 holds X(B). T1 requests X(B), creating T1→T2; T2 requests X(A), creating T2→T1 and a cycle. The DBMS aborts a victim and releases its locks so another transaction can continue. Do not treat blocked writes as completed. Victim choice and restart timing are implementation-dependent; without logs, do not claim T1 must be the victim.

T1 holds A, waits B → T2
T2 holds B, waits A → T1
cycle: T1 → T2 → T1

饥饿（starvation/livelock）是某事务长期得不到资源，但系统其他事务一直在进展，不必有等待环。公平队列或提高久等事务优先级可缓解。死锁检测是出现环后选择回滚；超时可能把仅仅很慢的事务也回滚，因此超时不是严格证明死锁。统一按A再B的资源顺序申请锁则可预防这种循环，代价是较少灵活性与可能提前持锁。

Starvation/live lock means one transaction waits indefinitely while others keep progressing, without requiring a cycle. Fair queues or ageing priorities help. Deadlock detection aborts after a cycle appears; timeouts can also abort merely slow transactions and are not proof of deadlock. Requesting resources consistently in A-then-B order prevents this cycle at the cost of reduced flexibility and potentially earlier lock retention.

等待—死亡（wait-die）：老请求者遇年轻持有者则等，年轻请求者遇老持有者则回滚。伤害—等待（wound-wait）：老请求者回滚年轻持有者，年轻请求者等老持有者。两者约束等待方向所以不会形成环，重启保留原时间戳以减轻饥饿。它们是基于时间戳的死锁预防，不能和下一节完全不用等待的TO算法混为一谈。

Wait-die lets an older requester wait for a younger holder, but aborts a younger requester facing an older holder. Wound-wait lets an older requester abort a younger holder, while a younger requester waits for the older holder. Their directed waiting prevents cycles; retaining the original timestamp on restart helps avoid starvation. These timestamp-based deadlock-prevention policies differ from the non waiting TO algorithm below.

时间戳排序：每步先检查再改状态Timestamp ordering: validate before changing state

来源 / Source: Lecture/Week11-CC.pdf · PDF p. 40-45（原资料留在本地版） · 本地逐页图文 / Local pages

基本时间戳排序（timestamp ordering，TO）给每个事务固定TS(T)，按它规定串行顺序。每数据项X存RTS(X)，表示允许读过X的最大事务时间戳；WTS(X)表示最后允许写者的时间戳。“最后”指时间戳序，不必等于最近墙上时间。允许晚到的老读者读时，RTS取max，不能直接改成这个更小的老时间戳。

Basic timestamp ordering (TO) assigns fixed TS(T) values defining the serial order. Each item X stores RTS(X), the maximum timestamp of an allowed reader, and WTS(X), the allowed last writer’s timestamp. Last refers to timestamp order, not necessarily wall-clock arrival. When an older reader arrives later, update RTS with max rather than replacing it with the smaller timestamp.

read_T(X):
　if TS(T)<WTS(X): abort T
　else read X; RTS(X)←max(RTS(X),TS(T))
write_T(X):
　if TS(T)<RTS(X) or TS(T)<WTS(X): abort T
　else write X; WTS(X)←TS(T)

读检查WTS，因为不能让老事务看到属于未来串行位置的写。写检查RTS，因为年轻事务已经读过旧状态，老事务再写会使其读错；写也检查WTS，防止老写覆盖年轻写。事务局部计算不改变数据库值或RTS/WTS。拒绝的操作不写入；事务回滚后需按恢复机制撤销它此前已做的有效写。

A read checks WTS to prevent an older transaction seeing a write from its future serial position. A write checks RTS because a younger transaction has already read the preceding state, and checks WTS to avoid an older write replacing a newer one. Local computations change neither database values nor RTS/WTS. Rejected operations do not write; recovery must undo earlier effective writes of an aborted transaction.

基本TO不会为锁等待，所以无死锁，但冲突可能反复回滚造成饥饿，而且基本规则本身不保证无级联或严格性。通常重启给新时间戳，这与wait-die/wound-wait保留老时间戳的策略不同。课程把“年轻事务优先”作为直观总结，更准确的操作依据仍是上面逐项不等式。

Basic TO does not wait for locks and is deadlock-free, but repeated aborts can starve transactions; the basic rules alone do not guarantee cascadelessness or strictness. Restart normally assigns a new timestamp, unlike wait-die/wound-wait’s retained timestamp. The course’s “younger transactions win” is intuition; the precise decisions follow the inequalities above.

Thomas写规则与被忽略的写Thomas’s write rule and ignored writes

来源 / Source: Lecture/Week11-CC.pdf · PDF p. 46-48（原资料留在本地版） · 本地逐页图文 / Local pages

Thomas写规则先检查TS(T)<RTS(X)，若是仍回滚；否则若TS(T)<WTS(X)，忽略这次已过时写；否则正常写。顺序非常重要：不能因为有更新的写就忽略一个已经破坏读者顺序的操作。它允许部分基本TO会拒绝的历史，属于更宽的视图等价讨论，不保证原始所有操作构成的冲突图都无环。

Thomas’s write rule first aborts if TS(T)<RTS(X). Otherwise, if TS(T)<WTS(X), ignore the obsolete write; otherwise execute it normally. The order matters: a newer write does not justify ignoring an operation that already violates a reader’s ordering. The rule admits histories basic TO rejects and involves broader view-equivalence reasoning; the original history’s full conflict graph need not be a cyclic.

例如r1(A),w2(A),c2,w1(A),c1，TS1<TS2：RTS(A)=TS1且WTS(A)=TS2，T1的最后写被忽略，最终保留T2值。若保留原w1画图有T1→T2与T2→T1；忽略后的实际有效写历史不再有反向覆盖。不要把“没有执行的写”仍算进最终数据库值。

For r1(A), w2(A), c2, w1(A), c1 with TS1<TS2, RTS(A)=TS1 and WTS(A)=TS2, so T1’s final write is ignored and T2’s value remains. Including the original w1 gives graph edges both ways; the effective history after ignoring it has no reverse overwrite. A write that was not executed must not affect the final database value.

与PostgreSQL实际隔离的联系Connection to PostgreSQL isolation

A2 Q4明确补充：PostgreSQL普通读基于多版本快照（MVCC），默认READ COMMITTED每条语句取新快照，不等同把每个SELECT都加课程S锁。更新仍持行锁，可能互等死锁。不要从2PL课堂规则直接推断所有PostgreSQL读写阻塞。第13章用两会话快照例子连接理论与实际。

A2 Q4 adds that ordinary PostgreSQL reads use multiversion snapshots (MVCC). Default READ COMMITTED takes a new snapshot for each statement and does not put the course’s S lock on every SELECT. Updates still hold row locks and can deadlock. Do not directly infer all PostgreSQL blocking behaviour from classroom 2 PL. Chapter 13 connects the theory through a two-session snapshot example.

总结与自测Summary and self-check

锁协议通过等待控制交错，TO通过拒绝违反时间戳顺序的操作控制交错。优先图判断已执行历史的冲突等价，等待图判断当前阻塞能否继续。每次解题写明使用Basic、Strict、Conservative还是Rigorous，是否允许升级/降级、是否含提交，否则同一读写序列可能有不同可行性。

Lock protocols control interleaving through waiting; TO rejects operations violating timestamp order. Precedence graphs test conflict equivalence of executed histories; wait-for graphs test current blocking. State Basic, Strict, Conservative or Rigorous, conversion rules and commit points, because feasibility can differ for the same read/write sequence.

自编练习：T1、T2都持S(X)，然后都请求升级X(X)，会怎样？

T1 and T2 both hold S(X), and both request X(X). What happens?

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

自编练习 / Author-created exercise

每个升级都被另一人的共享锁阻止，形成等待环。2PL不会自动消除这种升级死锁。可通过预先申请写锁、保守全量申请或检测后回滚等策略处理。

Each upgrade is blocked by the other shared holder, creating a wait cycle. 2 PL does not automatically prevent upgrade deadlock. Options include requesting write locks initially, conservative all-at-once acquisition, or detection followed by abort.
