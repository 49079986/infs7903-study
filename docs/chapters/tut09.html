T09-E1-A

写SQL找七月购买Widget类型产品的客户类别。

Write an SQL query to determine types of customers purchasing a specific product type Widget in July.

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

课程提供答案；附教学推导与必要更正 / Course answer with derivation and necessary corrections

按三个FK连接，筛ProdType=Widget与2025年7月，再DISTINCT客户类型。课程SQL没DISTINCT，会重复输出Type；原伪日期表达式不能直接在PostgreSQL执行。用>=7月1日且<8月1日可涵盖所有7月时间，不漏7月31日稍晚时间。

Join the three FK paths, filter Widget and July 2025, and select distinct customer types. The course omits DISTINCT and can repeat Types. Its month syntax is not directly executable in PostgreSQL. Ahalf-open July 1–August 1 interval includes every July timestamp.

SELECT DISTINCT c.Type
FROM Customer c JOIN Invoice i ON i.CustID=c.CustID
JOIN LineItem l ON l.InvID=i.InvID
JOIN Product p ON p.ProdID=l.ProdID
WHERE p.ProdType='Widget'
 AND i.date>=DATE '2025-07-01' AND i.date<DATE '2025-08-01';

Customer.Type与Product.ProdType的等值选择率？

What is selectivity of Type in Customer and ProdType in Product?

答案与推理 / Answer and reasoning

均匀时S(Type=v)=1/5=.2，S(ProdType=Widget)=1/10=.1。它是某个具体等值条件的比例，不是“列本身只有一个永恒的选择率”。本查询并未对Customer.Type筛某值，不能再给整体结果额外乘.2。

Under uniformity, S(Type=v)=1/5=.2 and S(ProdType=Widget)=1/10=.1. These are fractions for specific equality predicates, not universal properties of a column. The query does not filter one Customer. Type, so do not multiply its result by.2 again.

T09-E1-C

画查询树并逐步解释优化。

Draw a query tree and show step-by-step optimisation with explanations.

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

课程提供答案；附教学推导与必要更正 / Course answer with derivation and necessary corrections

规范树为πType(σ三连接条件∧Widget∧July(C×I×L×P))。①把Widget下推P、July下推I；②把乘积与等值条件换连接；③选I_July⋈C，再连L，再连P_Widget，或按成本选另一连接顺序；④向叶下推π：C留CustID,Type，I留InvID,CustID（筛完日期后），L留InvID,ProdID，P筛完后只留ProdID。各步都保留连接键。

Canonical:πType (σthree joins∧Widget∧July (C×I×L×P)). Push Widget to P and July to I; replace products with joins;chooseI_July⋈CthenLthenP_Widget, or another cost-justified order; push projections to leaves. Cretains CustID, Type; I retains InvID, CustID after the date filter; Lretains InvID, ProdID; Pretains ProdID after filtering. Keep every needed join key.

P1 ← πProdID(σProdType='Widget'(P))
I1 ← πInvID,CustID(σJuly2025(I))
C1 ← πCustID,Type(C)
L1 ← πInvID,ProdID(L)
R ← I1 ⋈ C1
S ← R ⋈ L1
T ← S ⋈ P1
RESULT ← πType(T)

What projection operations occur? Can any be performed immediately?

答案与推理 / Answer and reasoning

C可立即πCustID,Type；L可立即πInvID,ProdID。I必须先用Date筛，再πInvID,CustID；P先用ProdType筛再πProdID。若先πType(C)会丢CustID；先πInvID(L)会丢ProdID，无法筛Widget。最终πType负责去重，可在不再需要其他键后做。

Immediately project C to CustID, Type and L to InvID, ProdID. Filter Iby Date before dropping Date; filter Pby ProdType before keeping ProdID only. Projecting C only to Type or L only to InvID too early loses needed keys. FinalπTypededuplicates after all other keys become unnecessary.

答案与推理 / Answer and reasoning

课程提供答案；附教学推导与必要更正 / Course answer with derivation and necessary corrections

须先声明模型。对题解列出的三个输入，若J=N(1+log₂N)+M(1+log₂M)，J(10000,100000)<J(1000000,100)<J(100000,12000000)。若额外单独算R⋈T，J(100000,100000)介于第一与第二之间。题解某处把12000000×100000当成本，另处用J，混了nested loop与sort-merge。不同算法下不可宣称相同全局排名。也不应一边算I⋈L再算S⋈P，最后又无理由重复连接已在S中的I；上面C的线性连接树是完整可解释的一种。

State a model first. For the answer’s three inputs, with J=N(1+log₂N)+M(1+log₂M), J(10000,100000)<J(1000000,100)<J(100000,12000000). An additional R⋈Tcost J(100000,100000)falls between the first two. The reference mixes a product cost for nested loops with Jfor sort-merge; rankings are not universal across methods. Do not redundantly rejoin I without explanation after already including it in S. Part Cprovides one complete connected join tree.
