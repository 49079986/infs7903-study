视图与物化视图Views and materialised views

对应 A2 专项：视图、递归与物化刷新 / Assignment connection →

学习目标与三层模式Learning objectives and the three-schema architecture

来源 / Source: Lecture/Week02-Views.pdf · PDF p. 3-12（原资料留在本地版） · 本地逐页图文 / Local pages

本章目标是解释视图提供的逻辑独立性、权限边界和查询简化，手工重写视图查询，判断更新与刷新的区别。前置是第2章SELECT、GROUP BY、NULL与约束。三层模式中，外部模式是用户看到的数据接口，概念模式是整体逻辑结构，内部模式是物理表示；映射让其中一层变化尽量少影响其他层。

This chapter explains logical independence, privilege boundaries and query simplification through views, manual query rewriting, and the distinction between updates and refreshes. Prerequisites are SELECT, GROUP BY, NULL and constraints from Chapter 2. In the three-schema architecture, external schemas are user interfaces, the conceptual schema is the overall logical structure, and the internal schema is physical representation. Mappings reduce the impact of changes across layers.

普通视图（view）是命名查询（named query），保存定义，查询时根据当前可见的基表数据计算。它可以隐藏不需要的列、限定行或封装连接。例如教务处看学生身份与地址，专业管理者只看学号和专业。视图不是自动的安全保证：必须配合基表权限、视图所有者与角色设置，避免用户同时能绕过接口直接读原表。

An ordinary view is a named query whose definition is stored and evaluated against currently visible base data when queried. It can hide columns, restrict rows or encapsulate joins. An administrative role might see identity and addresses, while a programme role sees ID s and programmes. A view is not an automatic security guarantee: base-table privileges, ownership and roles must prevent direct access that bypasses the intended interface.

CREATE VIEW IT_Students AS
SELECT sid,name,age FROM Student WHERE major='IT';
GRANT SELECT ON IT_Students TO programme_reader;

查询重写：保留谓词与分组语义Query rewriting preserves predicates and grouping

来源 / Source: Lecture/Week02-Views.pdf · PDF p. 14-24（原资料留在本地版） · 本地逐页图文 / Local pages

查询修改（query modification）把视图名替换为定义中的关系与表达式，再把视图条件与用户条件合并。例如从IT_Students选age>19，实际语义是major=IT且age>19。若视图条件是major=IT OR major=MM，必须加括号后再AND age>19；否则运算优先级会让所有IT学生绕过年龄条件。

Query modification replaces a view reference with its defining relations and expressions, combining the view and user predicates. Selecting age>19 from IT_Students means major=IT and age>19. If the view condition is major=IT OR major=MM, parenthesise it before adding AND age>19; otherwise operator precedence lets all IT students bypass the age condition.

SELECT name FROM Student
WHERE (major='IT' OR major='MM') AND age>19;

对聚合视图不能机械地把所有外层WHERE拼进基表WHERE。Majors(major,mtotal)以COUNT(*)按major分组，外层mtotal>100是筛选分组结果，所以重写为HAVING COUNT(*)>100。对基表先筛人再数人与先数人再筛组，会产生不同含义。

For aggregate views, do not mechanically paste every outer WHERE into the base-table WHERE. Majors (major, mtotal) groups by major and uses COUNT(*); filtering mtotal>100 selects group results, so it becomes HAVING COUNT(*)>100. Filtering people before counting and filtering groups after counting have different meanings.

CREATE VIEW Majors(major,mtotal) AS
SELECT major,COUNT(*) FROM Student GROUP BY major;
-- Equivalent form of SELECT * FROM Majors WHERE mtotal>100
SELECT major,COUNT(*) FROM Student GROUP BY major HAVING COUNT(*)>100;

课程学生例子初始IT有Peter与Bill共2人、MM有Bob共1人。把Peter专业改为MM后，重新查询普通视图得IT=1、MM=2；只把Peter年龄改掉不影响按专业计数。原因是输出只依赖major和行存在性。此“依赖分析”也是后面增量维护的基础。

In the course student example, IT initially contains Peter and Bill, while MM contains Bob. Changing Peter’s major to MM makes the ordinary view show IT=1 and MM=2. Changing only Peter’s age does not affect counts by major, because the output depends on major and row existence. This dependency analysis also underlies incremental maintenance.

物化：用存储和维护换取重复计算Materialisation trades storage and maintenance for re computation

来源 / Source: Lecture/Week02-Views.pdf · PDF p. 25-30（原资料留在本地版） · 本地逐页图文 / Local pages

物化视图（materialised view）实际保存查询结果。普通视图像一张每次重新计算的工作表，物化视图像保存好的汇总快照。后者查询可能更快，但基表更新后可能陈旧。PostgreSQL 的普通物化视图需显式REFRESH，不能把课程对“应当维护”的概念描述误解为该软件默认自动增量刷新。

A materialised view physically stores a query result. An ordinary view resembles a worksheet recalculated on demand; a materialised view resembles a saved summary snapshot. Reading the latter can be faster, but base changes can make it stale. PostgreSQL’s ordinary materialised views need an explicit REFRESH; the lecture’s conceptual requirement to maintain them is not a promise of automatic incremental refresh by that software.

CREATE MATERIALIZED VIEW mv_dept_sal AS
SELECT deptno,AVG(sal) AS avg_sal FROM emp GROUP BY deptno;
REFRESH MATERIALIZED VIEW mv_dept_sal;

是否物化应比较一个时间窗口内的总成本：查询次数×每次节约，能否抵过刷新、写入维护和空间成本，并满足新鲜度要求。教学补充：若维护平均值，可以存SUM和COUNT，每增加工资s，就令sum增加s、count增加1，avg=sum/count；不能把旧平均值与新工资简单再平均，因为两者权重不同。

Choose materialisation by comparing total cost over a time window: can query frequency multiplied by per-query savings cover refresh, write-maintenance and storage costs while meeting freshness requirements? Teaching supplement: maintain an average using SUM and COUNT. Adding salary s increments sum by s and count by one, then avg=sum/count. Averaging the old average and new salary directly gives incorrect weights.

例如原有工资40与60，平均50；新增100后应为(40+60+100)/3=66.67，而不是(50+100)/2=75。增量维护复杂连接时还须考虑重复匹配、删除和分组消失，完整重算虽然昂贵，却容易定义。

For salaries 40 and 60, the average is 50. Adding 100 gives (40+60+100)/3=66.67, not (50+100)/2=75. Incremental maintenance of complex joins also requires accounting for repeated matches, deletions and disappearing groups. Full re computation can be expensive but has straightforward semantics.

更新视图与刷新视图是不同方向Updating through a view and refreshing a view have different directions

来源 / Source: Lecture/Week02-Views.pdf · PDF p. 31-45（原资料留在本地版） · 本地逐页图文 / Local pages

视图可更新性（view updateability）讨论用户对视图做INSERT/UPDATE/DELETE时，能否明确映射到基表行。刷新讨论基表改后如何重新得到物化结果。前者是视图到基表，后者是基表到物化视图。聚合值AVG=5通常有无限多组基表值对应，所以默认没有唯一逆操作。连接视图删除一行时，也不清楚应删员工、部门还是关联记录。

View update ability asks whether INSERT/UPDATE/DELETE through a view can map unambiguously to base rows. Refreshing asks how to re compute a materialised result after base changes. The first direction is view to base table; the second is base table to materialised view. An aggregate such as AVG=5 usually has infinitely many underlying value combinations, so no unique inverse update exists. Deleting a joined row can likewise leave ambiguity about deleting an employee, department or association.

课程采用保守规则：单表并保留主键的简单视图可更新；聚合、DISTINCT、GROUP BY、集合运算和多表连接通常不可直接更新。实际PostgreSQL 17 对简单单表视图并不要求在输出中暴露主键。缺少主键列的INSERT仍可能因为基表主键无默认值而失败；这不等于该视图所有UPDATE/DELETE都不允许。考试解释题应说明课程规则，软件操作题再写明具体DBMS规则。

The course uses a conservative rule: simple single-table views retaining the primary key are updateable; aggregation, DISTINCT, GROUP BY, set operations and joins generally are not directly updateable. PostgreSQL 17 does not require a simple single-table view to expose its primary key. An INSERT omitting a mandatory base key may fail without a default, but that does not prohibit every UPDATE or DELETE through the view. State the course convention in conceptual answers and the specific DBMS rule in software tasks.

PostgreSQL 17 · Automatically updatable views

WITH CHECK OPTION 约束的是通过视图新增或修改后的行仍须满足视图谓词。例如只显示gpa≥6的视图，把某行改为5：无该选项时基表可能更新成功、行从视图消失；有该选项时拒绝。它不是用来撤销所有基表更新的全局CHECK，也不让聚合视图自动拥有逆映射。

WITH CHECK OPTION requires rows inserted or updated through a view to satisfy its predicate afterwards. In a view showing gpa≥6, changing a row to five can succeed in the base table and make it disappear from the view without the option; with it, the change is rejected. This is not a global CHECK on all base updates and does not create an inverse mapping for aggregate views.

INSTEAD OF 触发器（第4章）能为连接视图定义具体写入行为。例如界面提交一个姓名，由触发器先确认姓名恰好匹配一人，再把人的键写入关联表。这是开发者显式指定语义，不能声称DBMS从连接定义自动推断出唯一操作。

An INSTEAD OF trigger in Chapter 4 can define explicit write behaviour for a join view. For example, a form submits a name, the trigger confirms exactly one matching person, then inserts that person’s key into an association table. The developer supplies the semantics; the DBMS does not automatically infer a unique action from the join definition.

The preparation file creates EMP, DEPT and copies EMP1, DEPT1; the course example has 50,005 rows per EMP table and nine per DEPT table. prep-4.sql is absent locally, preventing reproduction of random salary values and timings. Create V_EMP_ACC for deptno=30, insert employee 3035 NICK COLES, then rename that row JAMES ADAM through the view. Verify it in the base table with WHERE empno=3035 to establish propagation. Department 30 has different names across practical datasets, so inspect the actual DEPT data.

CREATE VIEW v_emp_acc AS
SELECT empno,ename,job,hiredate,sal,deptno FROM emp WHERE deptno=30;
INSERT INTO v_emp_acc VALUES(3035,'NICK COLES','ENGINEER',DATE '2015-01-01',70000,30);
UPDATE v_emp_acc SET ename='JAMES ADAM' WHERE empno=3035;
SELECT * FROM emp WHERE empno=3035;

随后把视图改为COUNT与AVG，观察它不再默认可更新；再创建按部门工资汇总的普通视图与物化视图，使用\timing和EXPLAIN ANALYZE比较。普通视图计划扫描基表、连接、聚合；物化视图只扫描已存储的9行。课程前面修改EMP而没改EMP1，导致某些平均值不同：性能对比前应确认输入是否一致，不能把输入不同误判成“物化产生错误”。

Next redefine the view using COUNT and AVG and observe that automatic update ability no longer applies. Create ordinary and materialised salary summaries, comparing them with \timing and EXPLAIN ANALYZE. The ordinary plan scans, joins and aggregates base data; the materialised plan scans nine stored rows. Earlier steps change EMP without changing EMP1, explaining differing averages. Confirm equivalent inputs before comparison rather than treating different inputs as incorrect materialisation.

总结、易错点与自测Summary, pitfalls and self-check

区分四件事：视图接口、查询重写、物化维护、通过视图更新。普通视图不会天然预先计算结果；物化视图不会天然实时同步；主键不是每个DBMS的可更新必要条件；一次查询更快不代表包含刷新成本后总成本更低。

Keep four issues separate: the view interface, query rewriting, materialised maintenance and updates through a view. Ordinary views do not inherently pre compute results; materialised views do not inherently synchronise in real time; exposing a primary key is not universally necessary for update ability; and a faster read does not prove lower total cost once refresh is included.

C3-S1

自编练习：视图筛选salary>50000，通过视图把某行改为45000会怎样？

A view shows salary>50000. What can happen if a row is updated to 45000 through the view?

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

自编练习 / Author-created exercise

若该简单视图可更新且没有CHECK OPTION，基表更新后行不再出现在视图；有CHECK OPTION则拒绝。还需满足基表约束与权限。判断不能只说“该行原来在视图中所以一定能改”。

For an updateable simple view without CHECK OPTION, the base update can succeed and the row disappears from the view. With CHECK OPTION, it is rejected. Base constraints and privileges still apply. Original membership in the view alone does not establish that the update is permitted.

C3-S2

自编练习：为什么刷新物化视图不能解决聚合视图的可更新性？

Why does refreshing a materialised view not make an aggregate view updateable?

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

自编练习 / Author-created exercise

刷新从已确定的基表状态算出结果；可更新性要求从一个期望结果反推出应改哪些基表值。前向计算可以唯一，逆向分配却可能不唯一，两个问题的方向不同。

Refreshing computes a result from a known base state. Update ability asks which base values should change to realise a desired view result. The forward calculation can be unique while the inverse allocation is ambiguous; the problems have opposite directions.
