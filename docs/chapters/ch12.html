INFS7903 · CH12

日志、检查点与恢复Logging, checkpoints and recovery

学习目标与失败类型Learning objectives and failure types

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 4-11（原资料留在本地版） · 本地逐页图文 / Local pages

目标是根据缓冲策略决定Undo/Redo，按日志顺序恢复值，解释WAL与检查点为何必要，并区分备份与崩溃恢复。前置是块/缓冲、第10章提交回滚及第11章严格性。事务失败通常回滚一个事务；系统崩溃丢失易失内存但磁盘仍在；介质失败可能丢磁盘内容，需要备份和保留下来的日志。不能只用内存里的日志恢复内存丢失。

The goal is to determine Undo/Redo from buffer policy, recover values in log order, explain WAL and checkpoints, and distinguish backups from crash recovery. Prerequisites are pages and buffers, commit/abort from Chapter 10 and strictness from Chapter 11. A transaction failure usually aborts one transaction; a system crash loses volatile memory while disk remains; media failure can destroy disk contents and requires backups plus surviving logs. A log existing only in lost RAM cannot recover that RAM.

缓冲管理器（buffer manager）把磁盘块复制到内存页，修改后内存页成为脏页（dirty page）。脏表示内存与磁盘版本不同，并非业务值非法。把页写回磁盘叫刷新（flush）。一个事务提交时，其数据页是否刷新，与日志是否持久化是两个独立问题；把它们分开，才能理解恢复。

The buffer manager copies disk blocks into memory pages. Modified pages are dirty: memory and disk differ, not necessarily that the business values are invalid. Writing a page back is a flush. Whether data pages flush at commit is separate from whether the log becomes durable. This separation is essential to recovery reasoning.

备份、转储与日志Backups, dumps and logs

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 12-17（原资料留在本地版） · 本地逐页图文 / Local pages

逻辑备份（logical backup）导出逻辑对象与数据，如SQL定义和行；单独CSV只保存部分内容，不自动包含约束、函数和权限。物理备份（physical backup）复制数据库存储表示，必须满足一致性要求并配合相关日志。冷备份在停止服务时做，热备份在运行时做但需要协调机制；直接随意复制正在变化的文件不保证可恢复。

A logical backup exports logical objects and data, such as SQL definitions and rows. A CSV alone is partial and does not automatically preserve constraints, functions or privileges. A physical backup copies storage representation and must meet consistency requirements with relevant logs. Cold backups stop service; hot backups run online but require coordination. Arbitrarily copying changing database files does not guarantee recovery.

备份是较早状态的副本；日志（log/journal）按顺序描述发生过的更新，能把恢复推进到备份之后。日志记录可包含事务ID、数据项、旧值前像（before image，BFIM）、新值后像（after image，AFIM）、开始、提交、回滚和检查点。实际系统不一定记录每次普通read，课件的read记录属于教学模型。

A backup copies an earlier state; a log/journal records ordered updates and can advance recovery beyond it. Records may include transaction ID, data item, before image (BFIM), after image (AFIM), begin, commit, abort and checkpoint. Real systems need not log every ordinary read; the lecture’s read records belong to its teaching model.

四种缓冲策略推导恢复需求Deriving recovery needs from four buffer policies

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 27-30（原资料留在本地版） · 本地逐页图文 / Local pages

偷写（steal）允许尚未提交事务修改过的页被写回磁盘，可能因缓冲空间不足。于是崩溃时磁盘可能含失败事务效果，需要Undo。No-steal阻止这些未提交效果进入数据磁盘，所以不需要为它们做物理Undo。它说的是修改页是否可落盘，不是“把BFIM写回去”；脏页通常含修改后的值。

Steal permits pages modified by uncommitted transactions to reach disk, for example under buffer pressure. A crash can therefore leave failed effects on disk and require Undo. No-steal prevents those uncommitted effects reaching data storage, avoiding their physical Undo. The policy concerns whether modified pages may flush; it does not mean flushing BFIM, since dirty pages normally contain modified values.

强制写（force）要求事务提交时其数据修改已写到数据磁盘，所以提交效果无需Redo；No-force允许提交后部分数据仍只在缓冲中，崩溃要用Redo恢复持久结果。No-force仍必须满足WAL的日志持久性，不能把“不强制数据页”误读成“不强制日志”。

Force requires a transaction’s data updates to be on data storage at commit, avoiding Redo for those effects. No-force allows some committed data to remain buffered, requiring Redo after a crash. No-force still requires durable WAL; not forcing data pages does not mean not forcing the log.

No-steal/Force最容易恢复，却需要容纳未提交修改的内存且每次提交写很多数据；Steal/No-force通常更灵活，代价是恢复逻辑更复杂。恢复表由两个独立问题推出，比死背四格可靠。No-Undo/No-Redo只是在该缓冲模型下不需要这两种崩溃动作，不表示介质失败不需要备份。

No-steal/Force simplifies recovery but needs memory for uncommitted changes and many data writes at commit. Steal/No-force is more flexible but requires more complex recovery. Deriving the matrix from two independent questions is better than memo rising it. No-Undo/No-Redo only concerns these crash actions under the model, not the need for backups after media failure.

WAL：先保留恢复证据，再允许不可撤回的动作WAL: preserve recovery evidence before risky actions

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 18-20（原资料留在本地版） · 本地逐页图文 / Local pages

预写日志（write-ahead logging，WAL）有两个核心顺序：数据页落盘前，它对应的恢复日志必须先持久化；向用户确认提交前，事务所需日志及提交记录必须持久化。第一条让未提交数据即使被偷写也能Undo，第二条让提交数据即使没写页也能Redo。日志可以顺序批量写，通常比每次提交随机写所有数据页更经济。

Write-ahead logging (WAL) enforces two orders: recovery log records must be durable before their data pages flush, and required transaction log records plus the commit record must be durable before acknowledging commit. The first enables Undo of stolen uncommitted pages; the second enables Redo of committed but un flushed data. Sequential batched log writes can be cheaper than forcing every modified data page at each commit.

原理例子：磁盘X=100，T1拟改200。先把(X,100,200)日志可靠保存，再允许X=200落盘；若T1失败，用100撤销。若T1已提交但X=200尚未落盘，重启读提交日志用200重做。如果先写页后写日志，崩溃可能既没有旧值也没有新值的可靠证据。

Example: disk X=100 and T1 proposes 200. Persist the log (X,100,200) before allowing X=200 to flush; if T1 fails, restore 100. If T1 commits but 200 has not flushed, recovery uses the committed log to redo 200. Writing the page before its log risks a crash without reliable evidence of the old or required new value.

为什么Undo反向、Redo正向Why Undo runs backwards and Redo forwards

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 23-26（原资料留在本地版） · 本地逐页图文 / Local pages

同一事务把X从100改200再改400，撤销时必须先恢复第二次写的BFIM=200，再恢复第一次写的BFIM=100。若正向Undo，先设100再设200，错误停在中间状态。重做则先200再400，保持原先因果顺序与最后写值。读日志时要按记录顺序而非简单按事务编号排序。

If one transaction changes X from 100 to 200 to 400, Undo must first restore the second write’s BFIM=200, then the first write’s BFIM=100. Forward Undo would set 100 then 200 and leave an intermediate state. Redo applies 200 then 400, preserving update order and the final value. Follow log-record order rather than sorting only by transaction ID.

课程p26日志中T1提交，T2与T3崩溃时未提交。T2对N先20→10再10→40，应反向40→10→20；T3把Y40→50，应恢复40；T1把X100→200→400，在No-force且页未可靠落盘的条件下重做到400。Last_lsn把同事务记录连起来，便于从最后记录向前追踪Undo。

In the p26 log, T1 committed while T2 and T3 were unfinished at the crash. T2 changes N20→10→40, so Undo reverses 40→10→20. T3 changes Y40→50 and restores 40. T1 changes X100→200→400 and redoes to 400 under No-force when its page is not known durable. Last_lsn links a transaction’s records for backward Undo travers al.

检查点的保证与不能跳过的旧日志Checkpoint guarantees and old log records that still matter

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 21-22（原资料留在本地版） · 本地逐页图文 / Local pages

检查点（checkpoint）减少恢复扫描范围，但要先读题给定保证。本课程多用简化完整刷新：暂停事务、按WAL顺序写必要日志与脏页、写检查点、继续。它不自动使活跃事务提交。真实系统可用模糊检查点（fuzzy checkpoint），不要求同时把全部脏页写完；本教材仅作必要区别，不扩展到完整ARIES。

A checkpoint reduces recovery work, but first identify its guarantees. The course mostly uses a simplified full-flush checkpoint: pause transactions, persist required logs and dirty pages in WAL order, record the checkpoint and resume. It does not commit active transactions. Real systems can use fuzzy checkpoints without flushing every dirty page together. This necessary distinction does not extend the syllabus into full ARIES.

“Undo只回到最近检查点”不能当成通则。若T4检查点前写了A=20但还没提交，完整刷新可能已把20落盘；崩溃后要Undo到15，其BFIM日志在检查点前，仍必须读取。类似地，延迟更新下T7检查点前写入日志、检查点后才提交，检查点时未提交效果不能被当成已持久化；Redo需要找到那条检查点前记录。

“Undo only back to the latest checkpoint” is not a general rule. If active T4 wrote A=20 before a full-flush checkpoint, that 20 may already be on disk; restoring 15 after a crash requires its pre-checkpoint BFIM record. Similarly, under deferred update, T7 can log a write before a checkpoint and commit afterwards. Its uncommitted effect is not durable at the checkpoint, so Redo must locate that earlier record.

延迟更新、立即更新与完整例子Deferred update, immediate update and a worked recovery

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 31-36（原资料留在本地版） · 本地逐页图文 / Local pages

延迟更新（deferred update）在提交前不把事务效果写入数据磁盘，常按No-steal/No-force教学模型处理：失败者忽略，不做物理Undo；提交者可能需Redo。立即更新（immediate update）允许提交前写页，按Steal/No-force需Undo失败者与Redo必要提交者。不要把延迟更新等同“完全不写缓冲”或“日志无须提前保存”，具体实现与教学抽象应区分。

Deferred update prevents transaction effects reaching data storage before commit, commonly modelled as No-steal/No-force: ignore losers without physical Undo, while winners may need Redo. Immediate update permits pre-commit data writes; Steal/No-force requires Undo of losers and Redo of required winners. Deferred update does not universally mean no buffer modification or no advance durable logging; distinguish implementations from teaching abstractions.

完整例子来自p24与pp33–36：T1改D10→20并在检查点前提交；T3改B20→15、T4改A15→20后检查点；之后T2改D20→15、T5改C15→30，T3与T2提交，随后崩溃。立即更新且完整刷新时：T1无需动作；T3的B已在检查点持久化；T2可能Redo D=15；T5、T4逆日志Undo为C=15、A=15。

Worked example from p24 and pp 33–36: T1 changes D10→20 and commits before the checkpoint. T3 changes B20→15 and T4 changes A15→20 before it. Afterwards T2 changes D20→15, T5 changes C15→30, T3 and T2 commit, then a crash occurs. With immediate update and full flushing, T1 needs nothing; T3’s B is already checkpoint-durable; T2 may require Redo D=15; Undo T5 then T4 to restore C=15 and A=15.

The p36 slide associates Redo of committed work with Steal/Force, contradicting its own matrix; this text uses No-force as the reason for Redo. Under deferred update, T3’s B requires Redo even though its log predates the checkpoint, because it was uncommitted then. Tutorial 12 T7 likewise needs C=31 from a pre-checkpoint record. Restarting losers is normally a higher-level policy, not an unconditional immediate step in every recovery algorithm.

影子分页与ADR的课程范围The course scope of shadow paging and ADR

来源 / Source: Lecture/Week12-Recovery.pdf · PDF p. 37-38（原资料留在本地版） · 本地逐页图文 / Local pages

影子分页（shadow paging）保留不变的影子页表，更新使用新的页与当前页表；提交时可靠地切换指向新页表的根，失败则仍用旧影子。它把“覆盖旧页”变成“写新页后切换引用”，但有页复制、碎片、垃圾回收和并发管理成本。根指针切换也必须原子且持久，不能假设普通内存赋值就完成提交。

Shadow paging preserves an unchanged shadow page table while updates use new pages and a current table. Commit durably switches the root to the new table; failure retains the old shadow. This replaces overwriting with copy-on-write and reference switching, at the cost of copying, fragmentation, reclamation and concurrency handling. The root switch itself must be atomic and durable; an ordinary RAM assignment is insufficient.

加速数据库恢复（accelerated database recovery，ADR）是课程提到的SQL Server特定恢复技术，目标包括更快恢复与回滚。理解其产品背景与目标即可，资料没有给出可手算的ADR内部算法，不应编造考试步骤。课程“瞬时回滚”的表述是产品特征描述，不能无条件推成任意数据库、任意操作都0耗时。

Accelerated database recovery (ADR) is the SQL Server-specific technique introduced by the course for faster recovery and rollback. Understand its product context and goals; the materials provide no detailed hand-calculation algorithm for ADR, so none is invented here. The slide’s instantaneous-rollback phrasing describes a product feature and should not become a zero-time guarantee for every database operation.

总结、英文作答与自测Summary, English answer patterns and self-check

恢复题先写缓冲策略、检查点保证与崩溃时提交集合，再区分需要哪些日志、哪些值已可靠落盘。英文论证：“Undo is required because steal may have propagated uncommitted changes to disk. Redo is required because no-force may leave committed changes only in volatile buffers.”接着给出具体事务、日志方向与目标值。

Begin recovery answers with buffer policy, checkpoint guarantees and the committed set at crash time. Then identify necessary log records and values already known durable. An English justification is: “Undo is required because steal may have propagated uncommitted changes to disk. Redo is required because no-force may leave committed changes only in volatile buffers.” Follow with transaction ID s, log direction and target values.

C12-S1

自编练习：为什么恢复可能还要读取检查点前日志？

Why is a pre-checkpoint log record sometimes needed during recovery?

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

自编练习 / Author-created exercise

活跃事务的修改可能在检查点被刷新，后来未提交就崩溃，需要旧BFIM撤销；延迟更新事务也可能检查点前记日志、之后提交，需要旧AFIM重做。能否跳过取决于检查点保证与事务状态，不仅取决于写发生的日期。

An active transaction’s update may flush at the checkpoint and later fail, requiring its earlier BFIM for Undo. A deferred transaction may log before the checkpoint and commit afterwards, requiring its earlier AFIM for Redo. Skipping depends on checkpoint guarantees and transaction state, not merely when the write occurred.

C12-S2

自编练习：No-steal/Force下，仅丢内存的崩溃需要Undo或Redo吗？

Under No-steal/Force, do you need Undo or Redo after a memory-only crash?

先独立尝试：写出条件、方法和理由，再展开。 / Try first: write the conditions, method and reasons before revealing the solution.

答案与推理 / Answer and reasoning

自编练习 / Author-created exercise

按该简单模型不需要：未提交效果没有落数据磁盘，提交效果都已强制写入。但若介质损坏或提交协议未原子完成，需讨论其他机制；题目所给假设界定结论范围。

Under this simple model, neither is required: uncommitted effects never reached data storage and committed effects were forced. Media failure or an incomplete atomic commit protocol raises other recovery questions. The stated assumptions define the conclusion’s scope.
