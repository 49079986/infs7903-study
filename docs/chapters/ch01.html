INFS7903 · CH01

关系模型与规范化Relational modelling and normalisation

学习目标与课程全景Learning objectives and the course as a whole

来源 / Source: Lecture/Week01-Intro.pdf · PDF p. 15-37（原资料留在本地版） · 本地逐页图文 / Local pages

本课程从数据库“内部如何工作”出发：SQL 说出需要哪些事实，关系代数组织查询，索引与文件结构定位记录，缓冲管理完成页传输，并发控制协调共享数据，恢复保证失败后仍可恢复。学完本章，你应能区分模式与实例、从函数依赖求候选键、判断范式，并解释分解的得失。

The course examines how a database works internally: SQL describes required facts, relational algebra organises queries, indexes and files locate records, buffer management transfers pages, concurrency control coordinates shared data, and recovery handles failures. After this chapter, you should distinguish schemas from instances, derive candidate keys from functional dependencies, identify normal forms and explain decomposition trade-offs.

前置知识补充：集合（set）不计顺序也不含重复；元组（tuple）是一组按属性定义的值。关系（relation）是同一模式下元组的集合。关系模式（relational schema）说明属性名、域和约束，关系实例（relation instance）是某时刻实际存储的元组。SQL 表默认可能含重复行，所以“关系”和实际 SQL 表不能在所有场合完全等同。

Prerequisite supplement: a set has neither ordering nor duplicate elements. A tuple is a collection of values defined over attributes. A relation is a set of tuples sharing a schema. A relational schema specifies attribute names, domains and constraints; a relation instance is the actual tuples at a particular time. SQL tables can contain duplicate rows by default, so relations and SQL tables are not interchangeable in every context.

元数据（metadata）描述数据，如列类型、主键、视图定义、权限和统计量；系统目录（system catalogue）保存这些描述。数据则是员工、工资等业务值。两者都最终以二进制存储，但用途不同：优化器查统计量选计划，执行器从数据页取实际记录。

Metadata describes data, including column types, keys, view definitions, privileges and statistics; the system catalogue stores these descriptions. Data consists of business values such as employees and salaries. Both ultimately use binary storage, but serve different purposes: the optimiser consults statistics to choose plans, while the executor fetches actual records from data pages.

函数依赖是对所有合法状态的约束Functional dependencies constrain every legal state

函数依赖（functional dependency，FD）X→Y 表示：对关系中任意两行 t₁、t₂，只要它们在 X 上相等，就必须在 Y 上相等。X、Y 都可以是一组属性。它说明“相同 X 不能对应不同 Y”，不是因果关系，也不是说 Y 在概念上不能离开 X 存在。一次样本中没有反例，仅说明该实例满足依赖，不能证明业务永远如此。

A functional dependency X→Y means that, for any two tuples t₁ and t₂, equality on X requires equality on Y. X and Y can each be sets of attributes. It means the same X cannot correspond to different Y values; it does not express causation or conceptual nonexistence of Y without X. A sample with no counterexample satisfies the dependency, but does not prove that the business rule always holds.

X → Y ⇔ ∀t₁,t₂ ∈ r(R),　t₁[X]=t₂[X] ⇒ t₁[Y]=t₂[Y]

例如 Emp(EID,Dept,DeptPhone) 中，EID→Dept，Dept→DeptPhone。员工号决定部门，部门决定统一联系电话，所以 EID→DeptPhone。若同一部门可以有多个独立电话且没有选定唯一电话，则 Dept→DeptPhone 不能成立。外键则表达包含关系：子表引用值必须出现在父表键中；不能把任意 FD 直接说成外键。

For Emp (EID, Dept, Dept Phone), suppose EID→Dept and Dept→Dept Phone. The employee identifies a department, which identifies its shared phone, so EID→Dept Phone follows. If a department has several independent phones without a designated unique one, Dept→Dept Phone does not hold. A foreign key instead expresses inclusion: referenced child values must occur in a parent key. An arbitrary FD is not automatically a foreign key.

前置知识补充：Armstrong 公理为自反性（Y⊆X 则 X→Y）、增广性（X→Y 则 XZ→YZ）、传递性（X→Y 且 Y→Z 则 X→Z）。由此可推出合并和分解规则。它们让我们从业务已知依赖推导隐含依赖，避免只盯着题目原样列出的箭头。

Prerequisite supplement: Armstrong’s axioms are reflexivity (Y⊆X implies X→Y), augmentation (X→Y implies XZ→YZ) and transitivity (X→Y and Y→Z imply X→Z). Union and decomposition rules follow. These rules derive implied dependencies from known business rules, so analysis must consider more than the arrows explicitly listed in a question.

属性闭包、超键与候选键Attribute closure, super keys and candidate keys

属性闭包（attribute closure）X⁺ 是在依赖集 F 下由 X 能确定的所有属性。算法从 X 开始，反复找左部已包含在当前集合中的依赖，把其右部加入，直到不能再扩张。属性只会增加且总数有限，所以必定停止；每次加入都有一条已满足的 FD 作依据，因此不会凭空推出属性。

The attribute closure X⁺ contains all attributes determined by X under F. Start with X, repeatedly find dependencies whose left side is already included, add their right side, and stop when nothing changes. Attributes only accumulate within a finite set, so the algorithm terminates. Every addition follows a satisfied FD, so no attribute is inferred without justification.

超键（superkey）能确定全部属性；候选键（candidate key）还要求最小，即去掉任何属性都不再是超键。主键（primary key）是选定的一个候选键。主属性（prime attribute）出现在至少一个候选键中。最小不是“长度最短”：两个不同大小的集合都可能各自无法再删，因此都是候选键。

A super key determines every attribute. A candidate key is additionally minimal: removing any attribute makes it cease to be a super key. A primary key is a selected candidate key. A prime attribute belongs to at least one candidate key. Minimal does not mean globally shortest: sets of different sizes can each be irreducible and therefore both be candidate keys.

Closure(X,F):
  result := X
  repeat
    old := result
    for each U -> V in F:
      if U is a subset of result: result := result union V
  until result = old
  return result

Tutorial 1 Ex1(i)：R(ABCD)，F={C→D, BC→A}。BC⁺：起点{B,C}，用C→D得{B,C,D}，再用BC→A得全部；B⁺只有B，C⁺只有CD，因此BC最小。B、C从未出现在任何非平凡依赖右部，无法由别的属性推出，所有键都必须包含BC，所以候选键恰好只有BC。

For Tutorial 1 Ex 1(i), R(ABCD) and F={C→D, BC→A}. BC⁺ begins as {B, C}, becomes {B, C, D} through C→D, then all attributes through BC→A. B⁺ is only B and C⁺ only CD, so BC is minimal. Neither B nor C appears on a nontrivial right side, so no other attributes can derive them; every key must include BC, making BC the only candidate key.

范式如何消除更新异常How normal forms reduce update anomalies

若部门电话重复写在每个员工行中，修改电话要更新多行；漏改一行产生修改异常。没有员工时无法单独录入部门是插入异常；删除最后一名员工顺带丢掉部门电话是删除异常。规范化（normalisation）把不同事实拆成适当关系，减少这些不必要的重复。仅声明 PK/FK 不会自动完成规范化，必须依据 FD 检查属性组合。

Repeating a department phone in every employee row means changing it requires many updates; a missed row causes a modification anomaly. Being unable to add a department without an employee is an insertion anomaly. Losing its phone when deleting the last employee is a deletion anomaly. Normalisation separates facts into appropriate relations to reduce unnecessary repetition. Declaring PK s and FKs alone does not normalise a design; attribute combinations must be examined using FDs.

范式 / Form准确检查 / Precise check例子与理由 / Example and reason
1NF

每个属性值在课程模型中是原子值。

Attribute values are atomic in the course model.

一格存一个电话，而非未建模的电话列表。

One phone value per cell rather than an un modelled list.

2NF

1NF，且每个非主属性完全依赖每个候选键。

1 NF, with every non prime attribute fully dependent on every candidate key.

BC为键而C→D，D非主：部分依赖，违反2NF。

BC is a key and C→D with non prime D: a partial dependency violates 2 NF.

3NF

每个非平凡X→A，X为超键或A为主属性。

For every nontrivial X→A, X is a super key or A is prime.

允许右部主属性的例外，不能只背“没有传递依赖”。

Allows a prime right-side exception; “no transitive dependency” alone is insufficient.

BCNF

每个非平凡X→Y，X必须为超键。

Every nontrivial determinant X must be a super key.

更严格，但分解可能失去依赖保持。

Stricter, but decomposition may lose dependency preservation.

Ex1(i) 的 C→D 是键BC的一部分决定非主属性D，所以最高仅1NF；分为ABC和CD。交集为C，且C→CD，连接不会生成伪元组，因此无损。两条依赖分别在一张表内检查，因此依赖也保持。例(ii) BC→ABD 的决定项BC本身为键，关系已是BCNF。

In Ex 1(i), C→D makes part of key BC determine non prime D, so the highest form is only 1 NF. Decompose into ABC and CD. Their intersection is C and C→CD, so the join introduces no spurious tuples and is lossless. Each original FD can be checked within one component, so dependencies are preserved too. In part (ii), BC→ABD has key BC as its determinant, so the relation is already in BCNF.

Ex1(iii) 的依赖是 BC→A、CD→AB、A→D。属性C无法由其他属性生成，键必须含C；依次检查BC、CD、AC都可推出全部，且删任一属性均不行。因此键为BC、CD、AC，A、B、C、D全部是主属性。A→D 中A不是超键，违反BCNF，但D是主属性，仍满足3NF。这正是必须用正式3NF定义的原因。

In part (iii), F={BC→A, CD→AB, A→D}. C cannot be derived from other attributes, so every key includes C. BC, CD and AC each derive all attributes and are minimal, giving those three candidate keys. All attributes A, B, C, D are prime. A→D violates BCNF because A is not a super key, but D is prime, so 3 NF still holds. This is why the formal 3 NF definition matters.

课程给出BCNF分解ABC、AD：交集A且A→AD，因此无损。然而CD→AB不能只靠这两张表的局部约束完整检查；C、D的组合无法跨表推出A。这说明“无损连接”和“依赖保持”是不同性质。无损保证拆开再连接能恢复原事实；依赖保持保证不用连接就能检查原依赖。选择3NF还是BCNF要说明取舍。

The course BCNF decomposition is ABC and AD. Their intersection A determines AD, so it is lossless. However, CD→AB cannot be fully enforced through only the local constraints of those two tables: C and D together cannot derive A across them. Lossless join and dependency preservation are separate properties. Lossless ness reconstructs the original facts, while dependency preservation permits checking original FDs without joining. Explain the trade-off when choosing 3 NF versus BCNF.

总结、常见错误与自测Summary, mistakes and self-check

先确认业务 FD，再算闭包和全部候选键，最后判断范式与分解性质。常见错误是从现有样本猜出永恒依赖、把所有决定项称为键、只检查被选作主键的候选键、认为BCNF分解一定保持全部依赖。规范化会增加连接需求，第3章视图可隐藏复杂性，第8–9章解释如何减少连接成本。

Establish business FDs first, compute closures and all candidate keys, then assess normal forms and decomposition properties. Common mistakes are inferring permanent rules from a sample, calling every determinant a key, checking only the chosen primary key and assuming BCNF always preserves dependencies. Normalisation can increase joins; views in Chapter 3 hide complexity and Chapters 8–9 address their cost.

答案与推理 / Answer and reasoning

自编练习 / Author-created exercise

A⁺=ABC，B⁺=BC，C⁺=C，唯一候选键A。单属性键不存在对键真子集的非主属性部分依赖，所以2NF；B→C中B非超键、C非主属性，违反3NF。可分为AB与BC，交集B决定BC，无损且依赖保持。

A⁺=ABC, B⁺=BC and C⁺=C, so A is the only candidate key. A single-attribute key has no non prime partial dependency on a proper subset, giving 2 NF. B→C violates 3 NF because B is not a super key and C is non prime. AB and BC form a lossless, dependency-preserving decomposition because their intersection B determines BC.
